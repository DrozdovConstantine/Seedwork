# SeedWork.Messaging

Общие контракты публикации и consumers для .NET 10. Подключите адаптеры
`SeedWork.Messaging.RabbitMQ` и/или `SeedWork.Messaging.Kafka`.

Подробные руководства с пошаговым запуском и примерами:

- [RabbitMQ: 15 примеров](../SeedWork.Messaging.RabbitMQ/README.md) — Topic/Direct/Fanout,
  очереди, классы конфигурации, повторы, error queue и телеметрия.
- [Kafka: 14 примеров](../SeedWork.Messaging.Kafka/README.md) — ключи, партиции,
  consumer groups, сканирование Assembly, повторы, пауза при ошибке и телеметрия.
- [Готовые сервисы Publisher и Consumer](../../samples/Messaging/README.md).

```csharp
public sealed record OrderCreated(Guid Id);

public sealed class OrderConsumer : IConsumer<OrderCreated>
{
    public Task ConsumeAsync(MessageContext<OrderCreated> context, CancellationToken ct)
    {
        // Обработка должна учитывать повторную доставку.
        return Task.CompletedTask;
    }
}

await publisher.PublishAsync("orders", new OrderCreated(Guid.NewGuid()),
    new PublishOptions { Key = "customer-42" }, cancellationToken);
```

Маршрут явно связывает тип сообщения с именованным подключением и назначением.
Один вызов отправляет в один маршрут. Регистрация `AddSeedWorkMessaging` вызывается
один раз; внутри можно зарегистрировать несколько подключений обоих типов.
Запускать публикацию после `IHost.StartAsync`. Настройка фиксируется до запуска;
изменение builder/options после регистрации не поддерживается.

## Автоматическая регистрация консумеров

Внутри `AddRabbitMq` или `AddKafka` вызовите
`AddConsumersFromAssembly(assembly)` — один вызов для всех подписок
выбранного транспорта в переданной сборке.

**Изменение API:** `RabbitMqConsumerAttribute` и `KafkaConsumerAttribute` удалены.
Перенесите настройки подписок в классы конфигурации или зарегистрируйте их через `Consume`.

Адаптер находит классы конфигурации для конкретных `IConsumer<T>`, включая
унаследованные реализации интерфейса. Абстрактные классы, незакрытые generic-типы
и консумеры без класса конфигурации выбранного транспорта пропускаются.
Настройки по умолчанию передаются методу `Configure(options)`, затем проверяются
и регистрируются через существующий механизм `Consume`.

Exchanges и topics описываются настройками консумера либо через `Exchange` / `Topic`.
Совпадающие объявления объединяются, конфликты отклоняются в конце настройки подключения
независимо от порядка вызовов. Подключения и маршруты публикации настраиваются на уровне шины.
Класс с несколькими `IConsumer<T>` может иметь отдельный класс конфигурации для
каждого контракта. Для одной пары в одном транспорте допускается один класс конфигурации.

Класс получает `RetryOptions` со стандартными значениями: `MaxRetries = 0`,
`Interval = 1 с`, `MaxInterval = 30 с`, `Exponential = false`, пустые `Handle` и `Ignore`.
Он может изменить любое значение, включая `Clear()` для фильтров.
Политику можно заменить целиком:

```csharp
options.Retry = RetryOptions.NoRetry(); // Одна попытка.
options.Retry = new RetryOptions { MaxRetries = 3, Interval = TimeSpan.FromSeconds(2) };
```

NoRetry() каждый раз создаёт отдельный объект. Null не допускается.
Без повторов первая ошибка
сразу приводит к error queue RabbitMQ либо паузе партиции Kafka.

**Изменение совместимости:** ранее отсутствие настройки включало три повтора.
Теперь для сохранения этого поведения необходимо явно указать MaxRetries = 3.

Классы конфигурации должны находиться в сканируемой сборке вместе с консумерами и
иметь публичный конструктор без параметров. Метод `Configure(options)` задаёт значения
подписки в коде; временный DI-контейнер для создания классов не строится.
При регистрации консумеры остаются scoped, зависимости их конструкторов разрешает DI.

Имя endpoint по умолчанию: `{connection}/{consumer.FullName}/{message.FullName}`.
Его можно явно задать конфигурацией. Повторное сканирование либо
сочетание сканирования с ручной регистрацией той же пары в том же подключении
завершается ошибкой. Разные подключения и транспорты независимы.
Ошибки загрузки типов, дубли деклараций и неполные настройки обнаруживаются при регистрации.

Рефлексия применяется только при настройке; обработка сообщений остаётся типизированной.
Сканирование не рассчитано на trimming/NativeAOT: необходимые типы могут быть удалены,
а generic-регистрация создаётся во время выполнения. Для таких сценариев используйте
явную регистрацию `Consume` и отдельно проверьте совместимость сериализации и клиентов.

Примеры классов конфигурации приведены в README обоих адаптеров и в
`samples/Messaging/Consumer`.

## Обработка

На каждую попытку создаются новый DI scope и объект сообщения из исходного JSON.
По умолчанию выполняется одна попытка без повторов (MaxRetries = 0).
Для включения повторов явно задайте положительный MaxRetries; начальный интервал — одна секунда.
`RetryOptions` позволяет задавать число повторов, фиксированный/экспоненциальный
интервал, максимум интервала и наборы типов `Handle`/`Ignore`; `Ignore` приоритетнее.
Ошибки десериализации не повторяются. Отмена при остановке не является ошибкой
сообщения. Консумеры обязаны учитывать `CancellationToken` и завершаться при остановке.

Используется JSON (`System.Text.Json`, web defaults); `MessagingBuilder.Json`
настраивается до окончания регистрации. CLR-имя типа в сообщении не передаётся.
Контракты принадлежат сервисам. Совместимые изменения добавляют необязательные поля;
для несовместимых изменений заведите отдельный маршрут и exchange/topic версии v2.
Внешние сообщения могут не иметь MessageId; такой идентификатор остаётся null.

`PublishOptions.Key` — partition key Kafka / routing key RabbitMQ; null использует
настроенный routing key RabbitMQ и стандартное распределение Kafka.
Пользовательские headers — строки UTF-8. Префикс `sw-`, `traceparent` и `tracestate`
зарезервированы. MessageId создаётся при публикации, если не задан.

## Гарантии

Публикация ожидает подтверждения брокера. Потеря подтверждения или отмена ожидания
не означают, что брокер не получил сообщение. Возможны дубликаты.
Подтверждение обработки выполняется после успешного завершения консумера.
Библиотека не обеспечивает exactly-once, идемпотентность бизнес-действий или
атомарность с транзакцией БД. Outbox будет отдельной настраиваемой возможностью;
контракт `IMessageTransport` отделяет отправку от прикладного `IMessagePublisher`.

## Телеметрия

Зарегистрируйте `MessagingTelemetry.InstrumentationName` и имена используемых адаптеров
через `AddSource`/`AddMeter` в OpenTelemetry или через будущий
`SeedWork.Observability.AddSeedWorkInstrumentation`. Экспортёр настраивает приложение.
Трассы связаны W3C trace context. Метрики покрывают публикацию, обработку, длительность,
повторы и ошибки; адаптеры добавляют ошибки RabbitMQ и приостановленные Kafka-партиции.
В логи и теги не попадают тело и текст исключения; логируется тип исключения.

Полный пример двух независимых сервисов: `samples/Messaging` в репозитории.
