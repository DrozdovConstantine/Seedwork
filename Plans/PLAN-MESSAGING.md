## Решение и границы

Единые интерфейсы публикации и consumers для Kafka и RabbitMQ на .NET 10.
Оба транспорта доступны одновременно через именованные подключения и явные маршруты.

Пакеты:

- SeedWork.Messaging: контракты, DI-регистрация, маршрутизация, JSON и pipeline повторов.
- SeedWork.Messaging.RabbitMQ: RabbitMQ.Client 7.2.2, AMQP 0-9-1.
- SeedWork.Messaging.Kafka: Confluent.Kafka 2.15.1, обычные consumer groups.

Первая версия включает публикацию, приём, топологию, повторы, телеметрию и error queues
RabbitMQ. Саги, request/response и отложенная доставка не входят. Outbox сейчас не нужен;
позднее он добавляется как настраиваемая возможность. Шина не зависит от доменного пакета.

## Публичные контракты

```csharp
public interface IMessagePublisher
{
    Task PublishAsync<T>(string route, T message, PublishOptions? options = null,
        CancellationToken cancellationToken = default) where T : class;
}

public interface IConsumer<T> where T : class
{
    Task ConsumeAsync(MessageContext<T> context, CancellationToken cancellationToken);
}
```

PublishOptions содержит MessageId, CorrelationId, строковый Key и строковые Headers.
MessageId создаётся при публикации, если отсутствует. MessageContext содержит Message,
идентификаторы, Key, Headers, Endpoint и Attempt (первая попытка — 1).
Типы брокеров в общем контракте отсутствуют.

AddSeedWorkMessaging регистрирует AddRabbitMq / AddKafka, именованные подключения,
маршруты и endpoints. Один маршрут соответствует одному типу сообщения и назначению.
Публикация разрешена после запуска host. Настройки фиксируются при регистрации.
Консумер получает новый DI scope и заново десериализованное сообщение на каждую попытку.

Сообщения — JSON через System.Text.Json; метаданные — headers, trace context — W3C.
Префикс sw-, traceparent/tracestate зарезервированы. Нет загрузки CLR-типов из сообщения.
Контракты принадлежат сервисам; доменный IDomainEvent не является интеграционным контрактом.
Совместимые изменения добавляют необязательные поля; несовместимые используют отдельный
маршрут/exchange/topic версии v2. Общая сборка бизнес-событий не требуется.

## Автоматическая регистрация консумеров

В RabbitMqBuilder и KafkaBuilder добавлен метод
`AddConsumersFromAssembly(Assembly assembly)`.
Он сканирует переданную сборку и регистрирует подписки через существующий типизированный
`Consume`; рефлексия при обработке сообщений не применяется.

- RabbitMQ: `RabbitMqConsumerAttribute`, `RabbitMqConsumerOptions`,
  `RabbitMqConsumerConfiguration<TMessage, TConsumer>`.
- Kafka: `KafkaConsumerAttribute`, `KafkaConsumerOptions`,
  `KafkaConsumerConfiguration<TMessage, TConsumer>`.
- Атрибут и класс независимо задают подписку, топологию и все параметры повторов.
  Порядок: значения по умолчанию → атрибут → класс. Класс может переопределить любое
  значение и очистить Handle/Ignore; незатронутые значения сохраняются.
- Конфигурация имеет публичный конструктор без параметров и метод
  `Configure(options)`. Настройки подписки задаются в коде; дополнительный
  DI-контейнер не создаётся.
- Обнаруживаются конкретные классы с прямыми и унаследованными IConsumer-интерфейсами.
  Абстрактные, незакрытые generic-классы и консумеры без настроек выбранного транспорта
  пропускаются. Атрибуты с базовых классов не наследуются.
- Каждая пара «консумер — сообщение» настраивается отдельно. Консумеры и их конфигурации
  находятся в сканируемой сборке. Дубли деклараций, неподходящий тип сообщения и
  неполные настройки завершают регистрацию понятной ошибкой.
- Endpoint по умолчанию — `{connection}/{consumer.FullName}/{message.FullName}`;
  атрибут или конфигурация могут задать явное имя. Повторное сканирование и смешивание
  с ручной регистрацией той же пары в одном подключении запрещены.
- Топология берётся из итоговых настроек консумера: RabbitMQ ExchangeType; Kafka
  Partitions/ReplicationFactor. Отдельные Exchange/Topic необязательны. Общие объявления
  объединяются в конце настройки подключения: совпадающие принимаются, конфликты
  отклоняются независимо от порядка ручных вызовов и сканирования.
- RabbitMQ использует RabbitMqExchangeType.Topic по умолчанию в атрибуте, options и Exchange.
  Для Direct/Fanout тип указывается явно во всех объявлениях ресурса; конфликты отклоняются.
  Нулевые Partitions/ReplicationFactor Kafka берутся из общего объявления; для нового
  topic необходимы положительные значения. Настройки подключений и маршруты публикации
  остаются на уровне шины.
- Сканирование помечено RequiresUnreferencedCode и RequiresDynamicCode: trimming и
  NativeAOT требуют явной регистрации и отдельной проверки совместимости остальных компонентов.

Пример в samples/Messaging/Consumer показывает оба способа настройки. Unit-тесты проверяют отдельные сборки с корректными и ошибочными
декларациями; интеграционный сценарий проверяет доставку и повторы через оба брокера.

## Гарантии, топология и ошибки

Успешная публикация означает подтверждение брокера, а не выполнение consumer.
Потеря подтверждения и отмена ожидания дают неопределённый результат отправки.
Возможны дубликаты; идемпотентность бизнес-действий обеспечивает сервис.
Атомарность с транзакцией БД без outbox не обеспечивается.

Топология описывается отдельно для каждого брокера. ValidateOnly — по умолчанию,
CreateMissing — явная настройка. Проверки заканчиваются до запуска consumers.
Существующие ресурсы не пересоздаются и не изменяются автоматически; несовместимость
останавливает запуск. Адреса, секреты, SSL/SASL предоставляет приложение.

### Повторы

- Настройка для каждого endpoint: MaxRetries, Interval, Exponential, MaxInterval, Handle/Ignore.
- По умолчанию одна попытка без повторов (MaxRetries = 0). Повторы включаются явно;
  начальный интервал 1 секунда, Ignore приоритетнее Handle.
- Следующие сообщения той же последовательности ждут. Ошибки десериализации не повторяются.
- Отмена при остановке не отправляет сообщение в error queue и не фиксирует Kafka offset.
- Счётчик попыток относится к текущей доставке; перезапуск может начать попытки снова.

### RabbitMQ

**Ошибка → повторы → error queue → продолжение.**

Явные durable exchanges (topic/direct/fanout), durable quorum queues и bindings.
Consumer queue: single active consumer, prefetch=1, x-delivery-limit=-1 во избежание
удаления брокером после многократных возвратов. Последовательность действует внутри очереди.
Публикация: persistent messages, publisher confirms, mandatory routing.
Key переопределяет настроенный routing key.

После исчерпания попыток исходное тело, headers, тип ошибки, endpoint, число попыток
и исходные exchange/routing key отправляются в отдельную durable error queue
(`<queue>_error` по умолчанию).
Ack исходного сообщения — только после подтверждённой отправки ошибки.
Если это невозможно, соединение закрывается, исходное сообщение остаётся у брокера;
адаптер переподключается через ReconnectInterval (5 секунд по умолчанию).
Дубликаты error-сообщений допустимы. После отправки ошибки исходный порядок её
последующего ручного возвращения не гарантируется.

ValidateOnly использует RabbitMQ Management API (ManagementUri, UserName/Password из
Connection) для чтения типа/durability ресурсов, аргументов очередей и bindings.
CreateMissing использует эквивалентные AMQP declarations. Error queue входит в топологию.

### Kafka

**Ошибка → повторы → приостановка партиции → сигнал через телеметрию.**

Явные topics, количество partitions, replication factor и consumer groups.
Producer: idempotence, acks=all. Consumer: auto commit/store отключены, обработка
последовательна внутри партиции, партиции независимы. Polling продолжается во время
работы handler и паузы. На успешной обработке commit следующего offset выполняется
перед продолжением партиции; ошибка commit удерживает её до успеха/потери назначения.

После исчерпания повторов обработка партиции остаётся paused. Offset ошибочного
сообщения не фиксируется; продвижение за него запрещено. Другие партиции продолжают
работать. Error topic и автоматический пропуск отсутствуют. Ошибки JSON/tombstone
также ведут к паузе. При revoke/lost отменяется handler, его результат не коммитится.

Пауза существует в текущем назначении процесса. При переназначении чтение начинается
с сохранённого брокером offset, а пауза прошлого назначения снимается, в том числе
при возврате партиции тому же consumer. Перезапуск или новый владелец может получить
ошибочное сообщение снова. Сохранение паузы между экземплярами пока не гарантируется.
Данные ограничены retention брокера независимо от commit.
